# Design note: linking NIDM-Results into NIDM-Experiment graphs

**Status:** draft proposal for discussion (post-v5.0.0). Not a release blocker.
**Goal:** let PyNIDM **generate**, **query**, and **link** NIDM-Results documents
(produced by the `nidmfsl` / `nidmresults` exporters) as *derivatives* of a
NIDM-Experiment subject/session — without reimplementing the NIDM-Results spec.

## Principles

1. **Do not re-model NIDM-Results.** A NIDM-Results document is already a valid
   RDF provenance graph. PyNIDM owns the *linking* and the *query*, not the
   results model. Generation is delegated to the existing exporters.
2. **Reuse the existing derivative pattern.** The NIDM-Results bundle *is* a
   `nidm:DerivativeObject`, generated by a `nidm:Derivative` activity. No new
   top-level concept — so the existing `/derivatives` REST route and the
   person→association→activity→generated query traversal work unchanged.
3. **`link` is the primitive.** `query` reads what `link` produced; `generate`
   = run an exporter, then `link`.
4. **Results live in the dataset's `derivatives/`.** Require the NIDM-Results to
   be a BIDS derivative under `<bids_root>/derivatives/<pipeline>/...` of the same
   BIDS dataset the experiment file was built from. The locator is then a
   **relative `bids::` path**, identical to how `bids2nidm` records
   experiment-level filenames (`nfo:filename "bids::..."`, via the existing
   `_bids_filename` helper) — so the whole dataset (raw + derivatives + nidm.ttl)
   stays self-consistent and portable with no absolute paths. Because BIDS
   derivatives are subject/session/task/run-organized, the anchoring
   (subject, session, often the input scan) can be **inferred from the derivative
   path** via pybids, removing most manual flags. *Fallback:* an absolute
   `prov:atLocation file://...` + explicit `-subject` for results that genuinely
   live outside the BIDS tree or aren't BIDS-named.

## Linking convention

A subject-associated `nidm:Derivative` activity that `prov:used` the input
scan(s) and generated a `DerivativeObject` marked `dct:conformsTo` NIDM-Results.
These bridge triples are **identical in both output modes**:

```turtle
# already present in the experiment graph
niiri:session_ses1  a nidm:Session, prov:Activity ; dct:isPartOf niiri:project_p1 .
niiri:person_sub01  a prov:Person ; ndar:src_subject_id "sub-01" .
niiri:acqobj_bold1  a nidm:AcquisitionObject, prov:Entity ;
    nfo:filename "bids::sub-01/func/sub-01_task-rest_bold.nii.gz" .

# new: the bridging derivation
niiri:deriv_res_abc  a nidm:Derivative, prov:Activity ;
    dct:isPartOf              niiri:session_ses1 ;
    prov:used                 niiri:acqobj_bold1 ;
    prov:qualifiedAssociation [ a prov:Association ;
                                prov:agent   niiri:person_sub01 ;
                                prov:hadRole sio:Subject ] .

niiri:nidmresults_xyz  a nidm:DerivativeObject, prov:Entity ;
    prov:wasGeneratedBy  niiri:deriv_res_abc ;
    dct:conformsTo       <http://purl.org/nidash/nidm#NIDMResults> .
```

## Output modes (`--results-mode`)

The mode flag only changes *what follows the bridge* — same code path, one branch.

### Reference — **default**

The NIDM-Results bundle stays an intact file (its `prov:Bundle` / named-graph
structure preserved); the experiment graph carries only a **BIDS-relative
locator** plus a small summary so lightweight queries work without fetching:

```turtle
niiri:nidmresults_xyz  a nidm:DerivativeObject, prov:Entity ;
    prov:wasGeneratedBy niiri:deriv_res_abc ;
    dct:conformsTo   <http://purl.org/nidash/nidm#NIDMResults> ;
    nfo:filename     "bids::derivatives/fsl-feat/sub-01/sub-01_task-rest_nidm.ttl" ;
    nidm:softwareLabel "FSL FEAT" ;    # optional lightweight summary
    nidm:statisticType "T" .
```

Rationale: the experiment graph is a lightweight, portable manifest of pointers,
using the same `bids::` relative-path convention as experiment-level files; each
results bundle keeps its machinery intact. Best at scale (many subjects, large
statistic maps), and the whole dataset moves as one self-consistent unit.

Implications:
- The referenced results must be a BIDS derivative under the dataset's
  `derivatives/`; the locator is relative to the BIDS root (no absolute paths).
- A NIDM-Results export is often a *pack* (the `nidm.ttl` plus referenced
  statistic-map `.nii` files); the locator points at the RDF entry, and since the
  pack sits under `derivatives/`, its internal map paths stay BIDS-relative too.
- Detailed-results queries need a loader that resolves the `bids::` path (against
  the dataset root) and unions the bundle on demand; the inlined summary answers
  "has results / from what software / statistic type" without touching the file.

### Inline — opt-in (`--inline`)

Union the full results subgraph into the experiment graph. Turtle cannot hold
named graphs, so the bundle boundary is **intentionally flattened** into the
default graph:

```turtle
niiri:nidmresults_xyz  a nidm:DerivativeObject, prov:Entity, nidm:NIDMResults .
# + the entire exporter subgraph: StatisticMap, ContrastMap, ExcursionSet,
#   Peaks, Clusters, ErrorModel, SoftwareAgent, ...  (flattened)
```

Rationale: one self-contained file. Cost: larger graph and loss of the bundle
boundary — the accepted trade for choosing inline.

## Proposed command surface

```
# 1. build the experiment file from the BIDS dataset (existing tool)
pynidm bids2nidm -d /data/ds000X -o /data/ds000X/nidm.ttl

# 2. link an existing NIDM-Results derivative (already exported under derivatives/)
#    -d gives the BIDS root so the bids:: relative locator can be computed;
#    subject/session/task are inferred from the derivative's BIDS path.
pynidm nidmresults -nl /data/ds000X/nidm.ttl -d /data/ds000X \
    -results derivatives/fsl-feat/sub-01/sub-01_task-rest_nidm.ttl \
    [-subject sub-01] [--inline]          # default = reference (bids:: relative)

# ...or generate + link in one step (runs the exporter, then links)
pynidm nidmresults -nl /data/ds000X/nidm.ttl -d /data/ds000X \
    --generate --tool nidmfsl --feat-dir /data/ds000X/derivatives/fsl-feat/sub-01/analysis.feat

# query: existing route lists them; results-aware helpers/routes to be added
pynidm query -nl /data/ds000X/nidm.ttl -u /subjects/sub-01/derivatives
```

`--generate` pulls in the exporters, so they'd be an optional extra:
`pip install pynidm[results]`.

## Phasing (all post-5.0)

- **v5.1** — `pynidm results link` (reference default + `--inline`) and read/query
  of linked results. Self-contained, reuses merge + Derivative + query.
- **v5.2** — `pynidm results generate` wrapping `nidmfsl` / `nidmresults` behind
  the `[results]` extra.

## Decided (working assumptions)

- **Reference is the default**; `--inline` is opt-in and flattens the bundle.
- **Locator = `nfo:filename "bids::<relpath>"`**, relative to the BIDS root,
  reusing `_bids_filename` — same convention as experiment-level files. Absolute
  `prov:atLocation file://...` only as an out-of-tree fallback.
- **NIDM-Results must be a BIDS derivative** under the dataset's `derivatives/`.
- **Subject/session/task inferred** from the derivative's BIDS path (pybids),
  with explicit `-subject` as a fallback.

## Open questions for the call

1. **Lightweight summary fields** to inline in reference mode for queryability
   without fetching (software, statistic type, contrast name(s), map count, ...).
   How much is worth duplicating vs. requiring a fetch?
2. **Query-time resolution** strategy for referenced bundles: lazy load + union
   per subject on demand? cache the parsed bundle? resolve `bids::` against the
   dataset root or a user-supplied root?
3. **Input-scan (`prov:used`) inference.** Match the derivative's task/run BIDS
   entities to the raw acquisition object already in the graph — reliable enough
   to auto-wire, or require `-derived-from` when ambiguous?
4. **Multiple contrasts / maps per bundle.** One `DerivativeObject` per bundle
   (summary lists contrasts) vs. one per statistic/contrast map?
5. **Pipeline identity.** How to name/record the `derivatives/<pipeline>` source
   (e.g. `nidm:softwareLabel` + pipeline dir) so results from different pipelines
   on the same subject stay distinguishable.
